Q1

How should this be packaged?

⚖ The fork: single-file is instantly playable — double-click, no server, no install, easy to email or drop on a static host — but it grows awkward past ~1,000 lines. A bundled project is nicer to extend later but needs npm install before anyone can play. This is the only choice here that's expensive to reverse.
Q2

What should it look like?

🎨 Taste call: this drives palette, snake rendering, grid treatment, and typography. All three are equally achievable on canvas — it's purely about the feel you want. Cheap to change later.
Q3

What happens at the edge of the board?

⚖ The fork: walls-kill is the canonical rule and makes the board feel tense and finite. Wrap-around is far more forgiving and changes the whole skill ceiling — good scores get much longer. Making it a toggle means tuning and testing two difficulty curves instead of one.
Q4

How should difficulty scale?

⚖ The fork: this is the single biggest lever on whether the game feels good. Too slow at the start and it's boring; ramp too hard and it's unplayable by score 20. Presets alone let players self-select but the game never builds tension within a run.
Q5

Anything beyond classic snake?

⚖ The fork: extras are where scope grows fastest, and each one adds state, edge cases, and a new way for the game to feel unfair. Pure classic ships tighter and plays cleaner; the light set adds variety without much risk.
Q6

How do people control it?

⚑ Stakes: if you'll ever open this on your phone, touch support has to be designed in — retrofitting swipe handling plus the mobile-Safari scroll/zoom suppression is fiddlier than building it up front. Keyboard-only is meaningfully less work.
Q7

High scores and sound?

◇ Low risk: both are small, self-contained additions. Sound is synthesized with WebAudio — no audio files, so the single-file packaging stays intact. Default is muted, since browsers block audio before first input anyway.
